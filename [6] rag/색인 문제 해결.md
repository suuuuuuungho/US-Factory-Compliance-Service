# RAG 색인 문제 해결 기록

이 문서는 Part 63 RAG 색인 작업(SUU-75~82, SUU-80)을 진행하면서 발견된 모든 문제와 원인, 해결 여부를 정리한 것이다. 색인 데이터는 전부 지우고(2026-09-16), 아래 문제들을 근본적으로 고친 뒤 처음부터 다시 색인한다.

## 1. Subpart 이름을 지어내는 문제 (근본 원인 미해결 — 다시 고쳐야 함)

### 무슨 일이 있었나
- SUU-76 PoC: 11개 청크 전부에서 Claude가 실제 이름("Subpart XXXXXX") 대신 가짜 이름("Subpart RRR")을 만들어냄.
- SUU-79: "이름을 지어내지 마라"는 지시문을 프롬프트에 추가. → **효과 없음.** 이유: `doc_text`(조문 본문) 안에는 애초에 그 Subpart의 진짜 이름이 한 번도 등장하지 않는다(조문은 전부 "this subpart"라고만 지칭). 모델이 볼 수 있는 정보 안에 정답이 없으니 "지어내지 마라"고 해도 지어낼 수밖에 없다.
- 로컬 LLM(Qwen2.5-14B-Instruct) PoC에서도 완전히 동일한 현상 확인 → 모델 성능 문제가 아니라 **입력 데이터에 정답이 없는** 구조적 문제로 확인.
- SUU-82: `build_context_request`에 `subpart_name` 인자를 추가하고, `index_chunk`가 `node["heading"]`을 넘기도록 수정. 테스트(`test_instruction_states_the_real_subpart_name`)도 통과, 머지됨.

### SUU-82도 실제로는 안 고쳐졌다 (이번에 새로 발견한 버그)
SUU-82 머지 후 실제로 955개 청크를 재색인해봤더니, 여전히 엉뚱한 이름을 지어내는 사례가 나왔다.

```
chunk_key: ecfr/40/63/subpart-CCCCC/.../section-63.7342/0   ← 진짜 Subpart는 CCCCC
context_text: "This chunk belongs to Subpart RRR ..."        ← 여전히 잘못 지어냄
```

**원인:** `suu80_full_run_budget.py`(실행 스크립트)에서 `index_chunk`에 넘기는 `node`가 **그 청크 자신이 속한 조문(section) 노드**였다. 즉 `node["heading"]`은 `"§ 63.7342 What records must I keep?"` 같은 조문 제목이지, `"Subpart CCCCC—National Emission Standards..."` 같은 **Subpart 제목이 아니다.**

우연히 청크의 노드 자체가 "Table 1 to Subpart CCCCC..."처럼 헤딩에 Subpart 이름이 포함된 특수 케이스(표 청크)만 정상적으로 고쳐졌고, 대부분을 차지하는 일반 조문(section) 청크는 여전히 안 고쳐진 채로 남아있었다.

DB에서 확인한 결과: `ecfr_node` 테이블에 `node_type = 'subpart'`인 노드가 따로 있고, 거기에 진짜 이름이 들어있다.

```
node_key: 40/63/subpart-CCCCC
node_type: subpart
heading: "Subpart CCCCC—National Emission Standards for Hazardous Air Pollutants for Coke Ovens: ..."
```

### 진짜 고쳐야 할 것
`index_chunk`를 호출하는 쪽(색인 실행 스크립트)에서 `subpart_name`으로 넘길 값은 **그 청크가 속한 Subpart 노드**(`nodes_by_key[subpart_key]`, 예: `"40/63/subpart-CCCCC"`)의 `heading`이어야 한다. 청크 자신의 노드(`nodes_by_key[chunk["node_key"]]`)가 아니다.

- `build_context_request(subpart_name=...)` 자체(SUU-82의 코드 변경)는 맞게 만들어졌다 — 문제는 **호출하는 쪽에서 잘못된 값을 넘긴 것.**
- 다음 재색인 스크립트를 짤 때는 `subpart_name = nodes_by_key[subpart_key]["heading"]`으로 명확히 구분해서 넘겨야 한다. (테스트에서도 "청크 노드 heading과 subpart 노드 heading이 다를 때 subpart 쪽이 쓰이는지" 확인하는 케이스가 필요했는데, 기존 테스트는 이 구분을 검증하지 않아 버그를 못 잡았다.)

## 2. 청크가 너무 커서 임베딩이 실패하는 문제 (새로 발견, 미해결)

955개 중 일부가 아래 에러로 실패:

```
Embedding input too large error: 입력이 모델이 허용하는 최대 크기를 넘음
```

- `subpart-CC/section-63.655`: 청크 하나가 88,986자
- `subpart-EEE/section-63.1206`: 청크 하나가 88,591자
- `subpart-A/section-63.14`: 52,568자 (경계선 — context_text 길이에 따라 통과/실패가 갈림)

**원인:** 청크 나누는 기준(SUU-70)이 "section 하나 = 청크 하나"인데, 표가 아주 많은 조문은 section 하나가 몇 만 자씩 된다. 게다가 `ecfr_embed.py`가 `overflow_strategy: None`으로 자동 잘라내기 기능을 꺼놓은 상태라, 모델 한도를 넘으면 그냥 실패한다.

**빈 청크 필터(SUU-78)와는 다른 문제다.** SUU-78은 "글자가 하나도 없는" 청크를 거르는 것이고, 이건 "글자가 너무 많은" 청크를 처리 못 하는 것 — 정반대 케이스다. `select_subpart_chunks`의 빈 청크 필터는 정상 작동 중(코드 확인함, `chunk["chunk_text"].strip()` 체크 있음).

**고쳐야 할 것 (택 1, 다시 시작 전에 결정 필요):**
1. 너무 큰 section은 `(a)`, `(b)` 같은 문단 경계로 더 잘게 나눈다 (청크 분할 로직 확장).
2. `overflow_strategy`를 `None`이 아닌 값(예: 자동 자르기)으로 바꿔서 모델이 알아서 잘라 처리하게 한다 — 다만 이러면 뒷부분 내용이 임베딩에서 누락될 수 있음.
3. 이 몇 개(3~5개) 조문만 예외로 건너뛰고 나중에 별도 처리한다.

## 3. 동시 호출 개수 때문에 생기는 일시적 네트워크 에러 (설정 조정만 필요)

```
WinError 10035: A non-blocking socket operation could not be completed immediately
```

- `WORKERS = 15`로 동시에 너무 많이 호출하다 보니 윈도우에서 소켓이 밀려서 생긴 에러.
- 콘텐츠 문제가 아니라 **동시 실행 개수 때문에 생긴 일시적 오류** — 다시 시도하면 대부분 성공한다.
- 실제 영향받은 청크: `subpart-CC/63.670, 63.671`, `subpart-DD/63.693, 63.694` 등 5~6개.
- 로컬 LLM으로 천천히(동시 실행 적게) 진행하면 이 문제는 자연히 줄어들 것으로 예상.

## 4. 로컬 LLM으로는 "20~30분 안에 전체 색인"이 불가능함 (하드웨어 한계, 참고용)

- `qwen2.5:14b-instruct-q4_K_M`: 청크당 평균 56.5초(4-way 병렬), 이름 정확도 0/11 (Subpart 이름을 못 맞춤 — 위 1번 문제와 동일한 원인, 로컬/원격 모델 상관없이 발생).
- `gemma4:e4b-it-qat`: 빈 응답만 반환, 사용 불가.
- 단일 GPU에서는 동시 호출을 늘려도 컴퓨트가 겹쳐서 1.2~1.5배 정도만 빨라짐 (진짜 병렬이 아님).
- Part 63 전체(3,662개)를 로컬로 돌리면 대략 16시간+ 걸림 — Haiku(약 5분)와 비교해 40배 이상 느림.
- **1번 문제(Subpart 이름 지어내기)를 먼저 고치면, 로컬 모델도 Haiku와 동일하게 정확해질 수 있다** (진짜 이름을 프롬프트에 박아주는 방식이라 모델 종류와 무관하게 적용됨). 속도는 여전히 느리지만, 이제 "천천히 로컬로 진행 → 나중에 예산 생기면 Haiku로 전환" 계획을 세울 수 있다. 이때 재색인은 청크 단위 upsert라서 일부는 로컬로, 일부는 Haiku로 섞어서 처리해도 문제 없다(이미 색인된 건 건너뛰거나 덮어쓰기 가능).

## 5. 예산 초과 관련 (참고, SUU-80 재실행 시 재사용 가능한 패턴)

- 사전 추정(문자 수 기반)이 아니라 **API가 실제로 반환하는 `usage`(input/cache_write/cache_read/output 토큰)로 실시간 비용을 계산**해서, 목표 금액에 도달하면 즉시 멈추는 방식이 실제로 잘 작동했다 ($15.50 한도에 $15.62로 거의 정확히 멈춤).
- 이 예산 캡 방식은 다음 재색인 스크립트에도 그대로 재사용할 만하다.

## 6. 표 안 숫자가 셀 구분 없이 이어붙여지는 문제 (새로 발견, 미해결)

표(TABLE) 블록의 `text_content`가 모든 셀 글자를 그냥 순서대로 이어붙인 한 줄 문자열이다.

```
"Table 1 to Paragraph (a) Region Address State I Director, Enforcement and
Compliance Assurance Division, U.S. EPA Region I, 5 Post Office Square—Suite 100
(04-2), Boston, MA 02109-3912, Attn: Air Compliance Clerk Connecticut, Maine,
Massachusetts, New Hampshire, Rhode Island, Vermont. II Director, ..."
```

행/열 구분이 전혀 없다. 이 표는 글자 위주라 그럭저럭 읽히지만, **배출기준처럼 숫자가 여러 열에 걸쳐 있는 표**는 어떤 숫자가 어떤 항목(오염물질, 시설 종류 등)의 값인지 구분이 안 된다. 법규 준수 서비스에서 숫자를 잘못 알려주면 심각한 문제가 된다.

**원인:** `[2] db/pipeline/1_eCFR/ecfr_blocks.py`의 `_text_content(element)`가 `" ".join("".join(element.itertext()).split())`로 표 안 모든 텍스트 노드를 셀 경계 구분 없이 이어붙인다.

**다행인 점:** 원본 표 구조(`markup` 컬럼, TR/TD 태그가 살아있는 원본 XML)는 이미 DB에 그대로 저장돼 있다 — 데이터 자체가 유실된 건 아니고, 임베딩에 쓰이는 `text_content`로 변환하는 과정에서만 구조가 사라진다.

**고쳐야 할 것:** `_text_content`가 `kind == 'table'`일 때는 `markup`을 다시 파싱해서 행(TR)마다 줄바꿈, 셀(TD/TH)마다 구분자(` | `)를 넣은 마크다운 표 형태로 만들어야 한다. Part 63을 다시 적재(`ecfr_ingest.py`)해야 반영된다.

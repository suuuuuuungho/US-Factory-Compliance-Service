# 미국 공장 Compliance AI — 3분 요약

"이 규정, 우리 공장에 적용되나요?"

미국 공장이 환경청(EPA)에 이렇게 물으면 답장까지 보통 101일. 4건 중 1건은 6개월이 걸립니다.

기다리는 동안에도 서류는 내야 합니다. 틀리면 서명한 책임자가 개인 책임을 지고, 갱신이 늦으면 공장이 멈춥니다. 대상 공장 10곳 중 3곳에 이미 위반 이력이 있습니다.

답은 957쪽 규정집 안에 이미 있습니다. 찾아 주는 사람이 없을 뿐입니다.

이 서비스는 그 자리에서 근거 조문을 찾아 줍니다.

17일 · 1인 개발 · PR 254개 · 정답 조문 적중률 69% → 93% (2026.09.10 ~ 09.26)

17일 중 5일은 코드 없이 문제 정의에만 썼습니다.

실제 사용자에게 묻기 위해 텍사스 공장 환경 담당자 45명에게 직접 콜드메일을 보냈습니다.

## 문제

> 답은 있는데, 아무도 찾아 주지 않습니다.

아래 4가지 기준으로 문제를 정의하고, 만들고자 하는 서비스의 유효성을 판단했습니다.

- 반복해서 발생하는 문제인가
- 실수요가 증명되는가
- 실질적인 경제적 손실이 실재하는가
- 기존 해법의 한계는 무엇인가

미국 공장은 대기 배출 허가(Title V)를 받은 뒤 5년 내내 "우리 공장에 어떤 규정이 적용되는지"를 서류로 증명해야 합니다. 그 근거 규정집이 40 CFR Part 63입니다.

공장 환경 담당자 한 사람의 책상 위에 놓인 상황입니다.

1. 서류는 멈추지 않습니다.
    - 6개월마다 보고, 1년마다 인증, 5년마다 갱신, 초과 배출은 24시간 안에 신고.
    - 근거: 40 CFR 70.6(a)(3)(iii), 70.6(c)(5), 70.5(a)(1)(iii)
2. 서류마다 조항 번호를 적어야 합니다.
    - 빈칸은 안 되고, "비슷한 조항"을 적으면 틀린 서류입니다.
    - 근거: 텍사스 TCEQ, Title V Deviation Reporting and Permit Compliance Certification Guidance
3. 그런데 규정집이 957쪽입니다.
    - 조문 2,473개, 표 784개, 463만 토큰. 사람도 못 읽고, LLM 컨텍스트에도 통째로 안 들어갑니다.
4. 다 읽어도 소용없습니다. 8년간 136번 바뀌었습니다.
    - 지금 조문의 45%(1,126개)가 그 사이 바뀐 것입니다. 학습이 멈춘 LLM은 옛 조문을 답하거나 없는 조문을 지어냅니다.
5. 물어보면 101일. 보고 주기 6개월보다 답이 늦습니다.
    - 4건 중 1건(28%)은 6개월 넘게 걸리고, 문의 1,127건이 쌓여 있습니다. 변호사는 매번 쓰기엔 비쌉니다.
6. 틀리면 담당자 개인이 책임집니다.
    - 연간 인증서에 "사실이다"라고 서명하는 사람은 담당자 개인입니다.
    - 대상 시설 49,618곳 중 27.9%가 위반 이력. 2015년 이후 처분 9,998건, $958.8M. 갱신을 놓치면 공장이 멈춥니다.

매번 써야 하고, 조항 번호를 꼭 적어야 하는데, 다 읽을 수 없고, 읽어도 바뀌고, 물어봐도 늦고, 틀리면 내 책임입니다.

## 서비스 정의

> 대기오염물질 배출 허가를 받은 미국 제조업 공장의 환경·규제 담당자가 보고·인증·신고·갱신 서류를 쓸 때, 공장에 적용될 수 있는 조항 후보와 무엇을 확인해야 하는지를 최신 근거 조문과 함께 정리해 주는 서비스.

## 결과

> 정답 적중 69% → 93%.

평가셋은 지어내지 않았습니다. 실제 공장이 EPA에 물은 질문 102건(공식 판정서한)에서 질문과 정답 조문을 뽑았습니다.

- 정답 조문이 상위 5개 안에 (Hit@5): 69% >> 93%(+24%p)
- 검색 순서 품질 (nDCG@10): 0.437 >> 0.692(+58%)
- 인용 근거율 (지어낸 인용의 반대): 99.6%
- 답변 충실도 (RAGAS faithfulness): 0.95 (심판 LLM 채점)

### 어떻게 올렸나

단계마다 실험하고, 숫자로 채택/기각했습니다. 괄호 안은 nDCG@10 변화입니다.

1. 임베더 비교 실험: 일반 모델 대신 법률 특화 Kanon 2 채택 (+0.140)
2. 리랭커 비교 실험: 3종 비교 후 Kanon 2 Reranker 채택 (+0.124)
3. 하이브리드 검색 실험: 순서는 그대로지만 Recall@20 +0.03이라 채택 (+0.007)
4. 후처리 규칙 실험: 실패 사례를 직접 읽고 규칙 추가 (+0.063)
5. LLM 리랭크 실험: Hit@5 88% → 93% (+0.061)

### 어떻게 지키나

이 점수는 CI가 지킵니다.

합격선(nDCG@10 ≥ 0.66, Hit@20 ≥ 0.95, 인용 근거율 ≥ 0.96) 아래면 GitHub 병합이 자동으로 막힙니다.

## 데이터 신뢰성

> 한 번 틀린 조항 번호를 준 서비스는, 다시 쓰지 않습니다.

공장 담당자는 이 서비스가 알려 준 조항 번호를 서류에 적고, 자기 이름으로 서명합니다. 서비스의 신뢰는 곧 데이터의 신뢰입니다. 그래서 네 가지를 지켰습니다.

### 정확성

**저는 데이터가 예측대로 수집·파싱·적재될 거라 믿지 않는 사람입니다.** 그래서 정부 데이터에서 예측이 빗나간 곳 17개를 찾아 고쳤습니다.

- 수집: 받는 도중에 정부가 규정집을 고치고 있으면, 반은 옛 규정·반은 새 규정인 파일이 생깁니다. 받기 전과 후의 기준일을 비교해, 다르면 버리고 다시 받습니다.
- 파싱: 규정집에는 표가 784개 있고, 배출 한도 숫자는 대부분 표 안에 있습니다. 글자만 모으면 숫자가 뭉개져서, 칸 경계까지 살려 저장했습니다.
- 적재: 벌금 한 건이 여러 공장에 함께 붙어 있었습니다(2,511줄). 그냥 더하면 합계가 부풀려져서, 벌금은 처분 1건당 한 번만 더합니다.

### 일관성

**테이블 43개마다 계약서를 썼습니다. 한 칸이라도 어긋나면 CI가 병합을 막습니다.** AI 검색과 화면은 DB의 칸을 믿고 동작합니다. 칸 하나가 바뀌면 서비스가 깨집니다.

그래서 테이블마다 칸 이름, 값의 종류, 빈칸 허용 여부를 데이터 계약서(ODCS)로 고정했습니다. PR마다 CI가 실제 DB를 계약서와 대조하고, 다르면 병합을 막습니다.

### 추적성

**모든 적재에 버전을 붙이고, 원본은 손대지 않고 보관합니다.** 적재 한 번이 버전 하나입니다. 버전마다 원본 기준일, 파일 목록 지문, 파서 버전을 남기고, 검사를 통과한 버전만 서비스에 연결합니다.

원본 파일 4,915개는 지문으로 이름 붙인 폴더에 보관해 덮어쓸 수 없고, 모두 어느 버전에 쓰였는지 연결되어 있습니다. AI가 인용하는 조각 6,157개는 모두 원본 위치(규정집 줄 번호, 편지 PDF)를 가지고 있어, 답의 근거를 원본까지 되짚습니다.

### 최신성

**사람이 챙기지 않아도, 데이터는 스스로 최신이 됩니다.** 원본마다 바뀌는 주기를 확인하고, 그 주기에 맞춰 적재 일정을 세웠습니다. 매일 바뀌는 것은 매일, 매주 바뀌는 것은 매주 받아 넣습니다.

바뀐 게 없으면 넣지 않고, 바뀌면 새 버전으로 넣은 뒤 검사를 통과해야 공개합니다. 결과는 매번 Slack으로 옵니다.

## 어필 포인트 5가지

> 문제를 현장에 묻고, 숫자로 고르고, AI가 판정하지 못하게 만들었습니다.

① 만들고 끝내지 않았습니다. 실제 공장 담당자에게 직접 물었습니다.

텍사스 공장 45곳의 환경 담당자 45명에게 콜드메일을 보냈습니다.

목적은 두 가지입니다. 제가 정의한 문제가 현장에서도 맞는지 확인하고, 서비스 피드백을 받아 개선하는 것.

조항 번호를 어디서 찾는지, 한 달에 몇 시간 드는지, 개정을 어떻게 아는지, 무엇을 원하는지 묻고, 서비스를 직접 써 보고 틀린 곳을 알려 달라고 부탁했습니다.

② 실험을 통해 품질을 개선했습니다. 그냥 고른 것이 없습니다. 점수가 올라도 판단 하에 버렸습니다.

실험 9번, 채택 6, 기각 3. 임베더 2종, 리랭커 3종, LLM 2종, 하이브리드 가중치 132조합.

"좋다더라"로 고른 것이 없습니다. 전부 같은 평가셋 102건 위에서 전/후 숫자로 결정했습니다.

정답 조문을 고정으로 끼워 넣으면 +0.046이 올랐지만, 평가셋 정답을 미리 아는 꼼수라서 기각했습니다.

③ AI가 "적용됩니다"라고 말할 수 없게 만들었습니다.

AI가 판정하면 사람은 원문을 안 읽습니다. "참고용입니다" 문구로는 행동이 안 바뀝니다.

그래서 답변 JSON에서 판정 필드(`applies`)를 아예 없앴습니다. 시스템이 구조적으로 판정을 말할 수 없습니다.

대신 후보 조항 + 적용을 가르는 기준 + 확인 체크리스트를 주고, 모든 문장에 조문 근거를 답니다.

④ "이 코드 왜 이래요?"에 티켓 번호로 답할 수 있습니다.

Linear 티켓 286개(완료 258), 설계 파일 239개. 티켓 없이 시작한 기능이 하나도 없습니다.

티켓마다 왜 하는지·무엇을 바꾸는지·완료 기준을 설계 파일에 적습니다.

티켓 번호·브랜치·PR 제목·설계 파일 첫 줄이 서로 맞는지 CI가 검사하고, 설계 파일 없는 PR은 병합이 막힙니다.

혼자 만들었지만, 혼자만 아는 프로젝트가 아닙니다.

⑤ [TDD] AI의 "다 됐어요"를 믿지 않습니다. 테스트가 말하게 했습니다.

"완성"의 기준을 코드보다 먼저 테스트로 못 박았습니다.

Claude가 실패하는 테스트를 쓰고, Codex는 통과만 시킵니다. Codex는 테스트를 고칠 수 없습니다.

PR 254개마다 테스트 772개가 전부 다시 돌아, 옛 기능이 깨지면 병합 전에 잡힙니다.

검색·답변 품질도 같습니다. 실제 EPA 사례 102건 점수가 합격선 아래면 CI가 병합을 막습니다.

## 개발 방식

> 혼자 했지만, 팀처럼 일했습니다.

17일, PR 254개. 저는 방향을 정하고, 승인하고, 병합만 했습니다.

아래 8가지를 모두 스스로 했습니다.

1. 문제 정의
2. 서비스 기획
3. TDD 개발 자동화 Flow 구축
4. CI/CD 파이프라인 구축
5. 데이터 파이프라인 구축
6. RAG 구축 및 검색/답변 품질 개선
7. 백엔드/프론트엔드 구축
8. UI 화면(웹사이트) 구축

```text
사람 (아이디어·승인)
→ Claude Code (설계 + 실패하는 테스트 작성)
→ Codex (구현 + PR)
→ CI (테스트·데이터 계약·이름 규칙·품질 합격선, 4겹 검사)
→ 사람 (직접 병합)
→ CD (Render·Vercel)
→ Slack 알림
```

### 1인 개발이 가능했던 이유

1. "완성"이 코드보다 먼저 있습니다.
    - Claude가 실패하는 테스트를 먼저 씁니다. AI의 말이 아니라 테스트의 초록불이 완료입니다.
2. 테스트 설계 에이전트와 실행 에이전트를 분리했습니다.
    - Codex는 테스트를 고치거나 지울 수 없습니다(작업 규칙으로 금지). 자기 코드에 맞춰 테스트 시나리오를 고치는 일을 구조로 막았습니다.
3. 옛 기능이 깨지면 병합 전에 압니다.
    - PR 254개 × 테스트 772개. 손으로 254번 확인했다면 불가능한 일입니다.
4. 사람은 코드가 아니라 약속을 검토합니다.
    - "이 테스트가 무엇을 보장하는가"만 보고 병합합니다. 그래서 혼자서 17일에 PR 254개가 가능했습니다.

병합만은 자동화하지 않았습니다. 마지막 판단은 사람이 합니다.

- DB: PostgreSQL(Supabase)
- Backend: FastAPI, Render
- Frontend: Next.js, React, Tailwind CSS, Vercel
- CI/CD: GitHub Actions
- TDD 개발 자동화 Flow
    - 설계: Claude Code
    - 티켓관리: Linear
    - 구현, 테스트: Codex

    - 알림: Slack
    - 코드버전관리: GitHub

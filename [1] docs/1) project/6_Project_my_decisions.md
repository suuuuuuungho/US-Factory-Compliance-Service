## AI에 위임하지 않고 내가 직접 정한 판단한 사항

코드는 AI 에이전트가 구현했습니다. 아래는 제가 직접 정했습니다. 

1. 서비스 원칙을 정하였습니다. 
  - 판정하지 않고 근거를 준다. 
  - 근거 없는 말은 하지 않는다. 
 
2. 평가셋
  - 평가셋은 AI로 만들어 내지 않았습니다.
  - 실제 EPA(미국 환경청) 문의내역 판정 서한에서 실제 사례 102건을 추출하여 RAG 품질을 평가했습니다.
  
3. CI 테스트 통과 기준 설계
  - CI 테스트를 통과하는 기준은 감으로 정하지 않고, 실측결과를 보고 직접 정하였습니다. 

4. 개발 원칙 설계 
  [코드작성원칙]
  - Andrej Karpathy가 정리한 "LLM 코딩 에이전트의 실수 유형"을 CLAUDE.md 규칙으로 옮긴 공개 스킬을 가져와 개발흐름에 접목시켰습니다.
   1) 코딩 전에 생각하기: 짐작하지 말고, 헷갈리면 묻고, 선택지가 있으면 보여준다.
   2) 단순하게: 요청받은 것만 가장 짧은 코드로 만들고, 쓸데없는 기능이나 추상화는 넣지 않는다.
   3) 필요한 곳만 고치기: 요청과 관련된 줄만 바꾸고, 주변 코드는 건드리지 않는다.
   4) 목표를 정하고 확인하기: "성공이 뭔지"를 테스트로 정하고, 통과할 때까지 반복한다.

  [DB구축]
  - 일관되고 설명가능한 DB 구축을 위해 데이터 명세서, 계약서를 작성하였습니다.
  - `Google PAIR [Data Cards Playbook]` 원칙에 따라 이 데이터가 왜, 어떻게 만들어졌고, 어디에 써도 되고 어디엔 쓰면 안 되는지를 처음 본 사람도 바로 파악할 수 있도록 하였습니다.
  - Linux Foundation 산하 Bitol 프로젝트의 공개 표준인 `ODCS v3.1.0 양식`에 따라 표준 YAML 계약서 6개를 만들었습니다.   
  - CI가 PR마다 그 계약서와 실제 DB가 같은지 자동으로 검사하도록 하여, db 일관성을 유지하였습니다.

  [ClaudeCode,Codex_Context관리]
  - CLAUDE.md, AGENT.md 파일로 각 에이전트를 통제했습니다.
  - 설계(Claude)와 구현(Codex)을 명확히 역할을 나누어서, 각 에이전트의 컨텍스트가 오염되지 않게 했습니다.
  - Context는 30% 이상을 넘지 않게 하여, 컨텍스트를 적당히 유지하여 품질을 유지했습니다.(/compact skill 사용) 
  - 세션에서 어느 한 주제 구현이 마치면, /clear 하였습니다. 세션이 너무 길어지지 않게 관리했습니다.
  
  [Linear]
  - Linear 티켓을 발행하여, 모든 설계/구현 내용을 기록으로 남겨 언제든지 유지 보수 가능한 구조를 만들었습니다. 
  - 티켓 번호·브랜치 이름·PR 제목·설계 파일 첫 줄이 서로 같도록 `2_rules.md` 규칙과 CI 검사로 강제하였습니다. 

  [GitHub]
  - 병렬로 작업할 때, GitHub Branch가 충돌되지 않도록 Worktree를 생성하고 merge 하도록 강제했습니다.
  - Merge는 자동화하지 않고 사람이 직접 확인하고 merge 승인하도록 강제하였습니다.

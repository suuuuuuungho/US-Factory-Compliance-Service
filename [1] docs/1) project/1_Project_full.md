혼자 만들었지만, 혼자만 아는 프로젝트가 아닙니다.

## 문제 정의

### 문제 정의를 이해하기 위한 배경: 미국 제조업 공장에 대한 유해대기오염물질 배출 규제는 3단계로 이루어집니다.

[의회]   Clean Air Act (청정대기법)                          ← 법 제정
  ↓
[EPA]    CFR Part 63 (유해대기오염물질 배출 관련 규정, NESHAP)  ← 업종별, 배출물질별 세부 규칙 제정
  ↓
[공장]   Title V Permit (통합 대기 배출 허가) 취득             ← 취득해야 공장 운영 가능

Title V 허가 뒤 5년 동안 공장은 규제 준수 인증 문서를 주기적으로 작성해야 합니다. 이 서비스의 진입 지점은 여기입니다.

### 문제 구조화 및 해결

   [문제] 규정이 매우 커서 일일히 확인하기 어렵습니다. LLM 컨텍스트에 넣기도 매우 큰 크기 입니다. 
   [해결]: RAG를 사용합니다.
     - 코퍼스가 컨텍스트에 들어가지 않기 때문에(Part 63은 실측 약 463만 토큰) RAG는 필수적 입니다.(Anthropic 공식 문서에도, 20만 토큰(약 500쪽)이 넘으면 RAG를 권합니다.)
     - LLM은 학습시점 이후 개정사항을 모릅니다.
     - LLM은 조문 번호를 그럴듯하게 지어낼 수 있습니다. 서명하는 사람에게 지어낸 조문은 치명적입니다.
     - 실제로 Subpart XXXXXX를 placeholder로 인식해 다른 Subpart 이름으로 바꿔 부른 상황이 있었습니다.
     - RAG를 통해 질문에 맞는 조문 몇 개만 골라내줍니다. 모든 조문을 일일히 볼 필요 없습니다. 
   
   [문제] 해결법이 존재하지만 느리거나 비쌉니다. 
   [해결]
     - 이 서비스는 누구나 언제든지 접근하여 자유롭게 질문하고 적용 후보 조항과 근거를 확인할 수 있습니다. 
     - 변호사, 컨설턴트는 큰 비용이 발생하고, 고객이 여러명이기 때문에 많이 신경 못 써줄 수 있고, 즉각적인 답변도 기대하기 어렵습니다. 
  
   [문제] 규정이 자주 바뀝니다.(2018~2025년 기준 136건)  
   [해결]
     - 데이터를 한번만 적재하지 않았습니다. 개정되면 원문을 다시 받아 적재하는 파이프라인을 만들었습니다.
     - eCFR, Federal Register에는 개정이력 메타데이터가 있습니다. 이를 연결하였습니다. 

   [문제] 공장 실무자는 작성이 쉽지 않습니다.
   [해결]
     - 현장의 언어로 질문해도 관련된 조항을 찾을 수 있도록 검색 로직을 설계했습니다.
     - 검색/답변 품질 향상을 위해 다양한 조합을 실험하였고, 실험 결과를 기반으로 최적의 로직을 만들려고 노력하고, 개선하였습니다. 
     - 실제 공장이 미국 환경청에 물어본 질문을 추출하여 평가셋(골든셋)을 만들었습니다.
     - 이를 기반으로 검색/답변 품질을 평가하였습니다. 평가셋을 그럴듯하게 지어내지 않았습니다. 
     - 평가셋 양도 충분히 하였습니다. (102건)

   [문제] 잘못 작성하면 잃게 되는 경제적 손실이 실재합니다.
   [해결]
     - 모든 말에 조문 근거를 달았습니다. 
     - 답 형식(JSON)에서 판정 필드를 없애 "적용됩니다"를 구조적으로 못 쓰게 했습니다.
     - CI 합격선을 만들어, 평가를 돌린 뒤 기록된 점수가 선 아래면 병합이 막히게 하였습니다. 

### 서비스 정의

Title V 허가를 받은 미국 제조업 공장의 환경·규제 담당자가 

보고·인증·신고·갱신 서류를 쓸 때,

공장에 적용될 수 있는 조항 후보와 무엇을 확인해야 하는지를 

최신 근거 조문과 함께 정리해 주는 서비스.

### 서비스 타겟

1st. Title V Permit 허가를 받은 중소 제조 공장의 환경·규제 담당자. 
  1) 규제 준수 관련하여 반기 보고, 연간 인증, 초과 배출 신고, 갱신, 변경 신청 서류를 계속 써야 한다.
  2) 현장 말은 알지만 법률 용어와 규제 지식이 부족하다.
  3) 비싼 변호사나 컨설팅을 매번 쓰기 어렵다. 주로 중소 규모 공장이 여기에 해당한다.
  4) 연간 인증에는 책임자가 서명한다. 그래서 근거가 확실해야 한다.
  5) EPA에 공식 판정을 요청하면 회신까지 중앙값 약 3개월(101일)이 걸리고, 4건 중 1건 이상(28%)은 6개월 이상 걸린다. (CAA Dashboard 판정서한 199건 실측)

      > 왜 중소 공장인가? 대기업이 돈을 더 내지 않나? 
        대기업은 사내 법무팀과 외부 로펌이 있어 빈틈이 작습니다. 빈틈이 가장 큰 곳은 전담 인력이 없는 중소 공장입니다.
      > 중소 공장이 정말 곤란을 겪나? 
        위반율 27.9%는 대상 시설 49,618곳 전체 기준입니다. 법무팀이 있는 일부 대기업만의 숫자가 아닙니다. 
        CAA Dashboard 회신에서 판정을 요청한 개별 시설 이름으로 확인 가능합니다. 대기업은 없습니다.
      > 그 사람들이 AI를 믿겠나?
        그대로 믿으면 안 됩니다. 그래서 "판정하지 않고 근거를 준다"로 설계했습니다. 
        서명하는 사람이 원문을 직접 확인하게 만드는 것이 신뢰를 얻는 길이라고 봤습니다.
    
2nd. 공장의 문의를 받는 EPA와 주 환경청 담당자.
  1) 공장들이 "이 조항이 우리에게 적용되나요?"라고 자주 묻는다.
     * 공개된 판정서한 기준, Part.63관련 질문 총 1,127건(ADI 995 + CAA Dashboard 132). 
     * 비공개 판정문의는 이보다 훨씬 많을 것으로 예상.
  2) 이 서비스를 사용하면 답변 지연 시간과 소모가 줄어든다.

### 서비스 원칙

1. 판정하지 않는다. "적용됩니다"라고 말하지 않습니다. 후보 조항, 적용 여부를 가르는 기준, 확인할 체크리스트를 줍니다.

  > 왜 판정을 안 하나? 판정해주면 더 편하지 않나?
    판정은 법률 자문입니다. 틀린 판정을 믿고 서명하면 책임은 서명자에게 갑니다. 서비스가 그 책임을 질 수 없습니다.

  > "참고용"이라고 적고 판정해 주면?
    문구로는 사람의 행동이 바뀌지 않습니다. "적용됩니다"를 보면 사람은 원문을 안 읽습니다. 그래서 답 형식(JSON)에서 `applies`, `verdict` 같은 필드를 아예 없앴습니다. 약속을 문구가 아니라 구조로 지킵니다.

  > 판정이 없으면 쓸모가 줄지 않나?
    담당자가 막히는 곳은 결론이 아니라 "어디를 봐야 하는지"입니다. EPA 회신도 결론만 쓰지 않고, 어떤 조문의 어떤 조건 때문인지를 함께 설명합니다.

2. 근거 없는 말은 하지 않는다. 모든 기준 문장에 `40 CFR 63.xxxx(a)` 형식의 조문을 답니다.

## RAG 검색 품질 개선 과정

### 평가셋

1. 평가셋 
  - 실제 공장이 EPA에 물은 질문을 실제 판정서한에서 추출했습니다. 
  - 정답은 EPA가 그 서한에서 인용한 조문입니다. 
  - PoC할 때, 32건으로 했습니다. 
  - 골든셋 만들 때, 102건으로 늘렸습니다.
  - 주 지표: nDCG@10, 보조 지표: Hit@5·Hit@20·Recall@20.
  - 동점 폭 0.03: 102건에서 3건 차이는 우연일 수 있어, 0.03 미만은 "같다"고 설정했습니다.

    > 왜 평가셋을 판정서한으로 만들었나? 
      판정서한에는 실제 공장이 EPA에 물은 질문과 EPA가 직접 인용한 정답 조문이 짝지어 있습니다. 이것을 추출했습니다.

### 청킹, 색인

Contextual retrieval 사용
  1) `(b) The owner or operator shall...`만 떼어 놓으면 어느 업종, 어느 설비 얘기인지 모릅니다. 
  2) Anthropic의 Contextual Retrieval을 따라 청크마다 LLM이 2~3문장 설명을 쓰고, [설명 + 원문]을 함께 임베딩 하였습니다.
  3) 청크 = 조문 하나. 30,000자가 넘으면 `(a)`, `(b)` 문단 경계로 나누었습니다. (5,625개)
  4) 법령용 프롬프트: "어느 Subpart·업종인지 / 적용대상·정의·배출한도·모니터링 중 무엇인지 / 어떤 설비·물질·수치인지"를 쓰게 하고, 적용 판단 문장과 원문에 없는 숫자는 금지했습니다.

   > 실제로 부딪힌 문제: 
   Contextual retrieval 시범 색인(11청크) 표본을 제가 직접 읽어 보니,
   모델이 Subpart XXXXXX를 전부 "Subpart RRR"이라고 다른 Subpart 이름으로 바꿔 불렀습니다.
   처음엔 프롬프트에 "지어내지 마라"를 넣었지만 효과가 없었습니다.
   원인은 조문 본문에 자기 Subpart 이름이 한 번도 안 나와서("this subpart"라고만 씀), 모델이 알 방법이 없었던 것입니다.
   그래서 Subpart 노드의 제목을 프롬프트에 직접 넣도록 구조를 바꿨습니다.
   첫 수정 뒤 955개 재색인에서 같은 문제가 또 나와서(호출부가 조문 제목을 넘김), 색인을 전부 지우고 다시 고친 뒤 5,625개 전체를 색인했습니다.
   "전체 색인 전에 사람이 표본을 먼저 읽는 단계" 덕분에 전체가 오염되기 전에 잡았습니다.

## RAG 답변 품질 개선 과정

### 답변 

1. 답변 품질 개선 단계 흐름

  지표 4개(평가셋 v2 102건, EPA 판정서한 기반)
   - Subpart 적중 
   - 인용 Recall: 정답 조문을 답이 인용한 비율
   - 인용 근거율: 답의 인용이 넘겨준 조문 안에 있는 비율. 밖이면 지어냄
   - LLM as a Judge: gpt-5-mini 심판이 EPA 판단 근거와 비교, 0~2 

  1) 상위 5: "이 공장에 무슨 규정이 걸리나요?"라는 질문에, 가장 관련 있는 법 조문 5개를 찾아 보여주고 답하게 했을 때의 첫 성적입니다.
   - Subpart 적중: 0.931
   - 인용 Recall: 0.685
   - 인용 근거율: 1.000
   - LLM as a Judge: 1.667
   - 출발점. 

  2) 상위 5 + `프롬프트 수정` : 점수가 낮은 원인이 프롬프트에 있는지, 넘겨준 조문 수에 있는지 판단하기 위한 실험
   
    프롬프트 v2에서 바꾼 것 두 가지
    - Subpart는 코드만: 1단계에서 모델이 "Subpart M"이라고 쓰면 채점기가 "M"과 다르다고 봐서 틀린 걸로 처리된 경우가 있었습니다. Subpart는 약칭(M, PPPP)만 쓰게했습니다.
    - 적용 가능한 Subpart는 다 적기: 한 공장에 규정이 두 개 걸릴 때도 모델이 하나만 답하고 끝내곤 했습니다. 그래서 "걸리는 규정은 하나도 빼지 말고 다 써라"고 시켰습니다.

   - Subpart 적중: 0.941 (+0.010)
   - 인용 Rec all: 0.707 (+0.022)
   - 인용 근거율: 0.998 (-0.002)
   - LLM as a Judge: 1.686 (+0.019)
   - 판단: 큰 변화가 없음 > `프롬프트가 아니라 조문 수 문제`로 판단.

  3) 상위 10 + `프롬프트 수정` : 조문수를 5개에서 10개로 늘려보는 실험
   - Subpart 적중: 0.961 (+0.020)
   - 인용 Recall: 0.739 (+0.032)
   - 인용 근거율: 0.996 (-0.002)
   - LLM as a Judge: 1.775 (+0.089)
   - 판단: 가장 크게 오름. 대신 입력 토큰 15k→27k/건, 비용 $1.38→$1.79. > `채택`

     > 인용 Recall 0.739는 낮지 않나?
      검색 Recall@10(0.804)에 묶임. 놓친 정답 조문 71개 중 53개는 검색이 답변 모델에 넘겨주지도 않은 것. 넘겨준 조문만 보면 182개 중 164개 인용(90%). 답변 프롬프트로 올릴 수 있는 상한은 0.78이라 나머지는 검색 과제.

  4) 상위 10 + `프롬프트 수정` + `Subpart A 공통 조문 3개 항상 포함` (63.2 정의 · 63.7 성능시험 · 63.8 모니터링) : 실패 case를 살펴보니 Subpart A 미포함이 원인이였음. 
   - Subpart 적중: 0.971 (+0.010)
   - 인용 Recall: 0.785 (+0.046)
   - 인용 근거율: 1.000 (+0.004)
   - LLM as a Judge: 1.755 (-0.020)
   - 판단: 정답 인용에 Subpart A 조문이 있는 케이스 29건 중 20건은 그 조문이 상위 10에 다 올라오지 않았음, 지표가 올랐지만 채택하지 않음.

     > 지표가 좋아졌는데 왜 안 넣었나?
      ① 검색 결과와 상관없이 정해진 조문을 고정으로 끼워 넣는 건 평가셋의 정답을 미리 알고 맞추는 셈. 
      ② 입력 토큰 27k→44k/건(+60%), 비용 $1.79→$2.27. 심판 점수는 오히려 -0.02.
      ③ 바른 해법은 검색이 Subpart A 공통 조문을 상위에 올리도록 고치는 것 → 답변이 아니라 검색 쪽 과제로 넘김. run·점수는 기록으로 남김.

  6) RAGAS로 확인:  (최종 조합 102건, 심판 gpt-5-mini)
   - faithfulness 0.95 / context_precision 0.893.   

  7)  합격선을 정해 CI로 강제
   - Subpart ≥ 0.93, 인용 Recall ≥ 0.70, 인용 근거율 ≥ 0.96, 판정 기준 점수 ≥ 1.71
   - 평가를 돌린 뒤 선 아래면 GitHub 병합이 막힘.

## TDD 개발 자동화 

### 흐름


[사람]    구현하고 싶은 기능을 Claude Code(Plan Mode)에 초안 생성 요청
  |
[Claude] 초안 제시
  |
[사람]    수정 사항 Claude Code에 지시
  |
[Claude] 수정안 제시
  |
[사람]    승인 후 Linear 티켓 발행 지시
  |
[Claude] Linear 티켓 발행해서 변경 범위·완료 기준·설계 파일 작성 + 실패하는 테스트 시나리오 작성
  |
[Codex]  테스트를 통과하는 코드 구현 → GitHub PR 생성               
  |
[CI]     GitHub Action, <테스트 + 이름 규칙 + 설계 파일 + 데이터 계약 + 품질 합격선> CI 검사  
  |
[사람]   PR 확인 → 직접 merge                        
  |
[CD]    merge되면 Render(백엔드) · Vercel(프론트) 자동 배포    
  |
[알림]  Slack에 모든 과정 알림


### TDD가 1인 개발을 가능하게 한 이유

1. "완성"이 코드보다 먼저 있습니다.
   Claude가 실패하는 테스트를 먼저 씁니다. AI의 말이 아니라 테스트의 초록불이 완료입니다.

2. 시험지를 쓰는 AI와 푸는 AI를 분리했습니다.
   Codex는 테스트를 고치거나 지울 수 없습니다(작업 규칙으로 금지). 자기 코드에 맞춰 시험지를 고치는 일을 구조로 막았습니다.

3. 옛 기능이 깨지면 병합 전에 압니다.
   PR 254개 × 테스트 772개. 손으로 254번 확인했다면 불가능한 일입니다.

4. 사람은 코드가 아니라 약속을 검토합니다.
   "이 테스트가 무엇을 보장하는가"만 보고 병합합니다. 그래서 혼자서 17일에 PR 254개가 가능했습니다.

병합만은 자동화하지 않았습니다. 마지막 판단은 사람이 합니다.



### 역할

1. 사람: 
   [한다] 아이디어, 티켓 확인, PR 확인과 병합 
   [안한다] 코드 작성

2. Claude Code 
   [한다] 티켓, 설계, 실패하는 테스트 시나리오 작성 
   [안한다] 기능 구현 

3. Codex 
   [한다] 기능 구현, GitHub PR 생성
   [안한다] 테스트 수정·삭제, GitHub PR 병합

4. Linear 
   [한다] 티켓 보관, 상태판 (Todo → In Progress → In Review → Done) 
   [안한다] 코드·테스트 보관

5. GitHub 
   [한다] 코드 보관, PR, CI 검사(테스트 + 규칙 + 합격선), CD 배포 트리거
   [안한다] 사람 승인 없는 병합, main 직접 push

6. Slack 
   [한다] PR 열림·CI 실패·병합·배포 결과 알림 
   [안한다] 판단·실행 (알림만 받음)

    > 왜 테스트 작성자와 구현자를 나눴나? 한 에이전트가 다 하면 빠르지 않나?
      빠르지만, 한 에이전트가 둘 다 쓰면 자기 코드에 맞춰 테스트를 고칠 수 있음. 또 서로의 컨텍스트가 오염이 안됨.
    > 나누면 해결되나?
      테스트는 Claude가 설계 단계에서 먼저 쓰고, Codex는 테스트를 건드리는 것이 규칙으로 금지했습니다.
      "무엇이 완성인가"를 정하는 쪽과 "만드는" 쪽이 달라야 검증이 의미가 있다고 생각합니다.
    > 병합은 왜 사람이 하나? 
      AI에 모든 것을 위임하지 않습니다. 중요한 판단은 사람이 개입하도록 하였습니다.

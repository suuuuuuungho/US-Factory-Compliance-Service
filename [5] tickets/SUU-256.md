# SUU-256 feat(db): 판정서한 128건을 청크로 잘라 임베딩해 적재

## 목표
decision-letters.json 의 서한 128건(pdf_url 있는 것) 본문을 문단 단위 청크로 잘라 Kanon 2 벡터와 함께 `rag_chunk`에 넣는다. release_id 는 기존 adi release 라 eCFR 검색(`/ask`)에는 절대 안 보인다.

## 건드릴 파일
- 만들 것: `[2] db/pipeline/4_ADI+CAA/letter_chunk.py`
  - 상수 `LETTER_RELEASE_ID = "5cc370d0-c513-4376-981f-2d910b39ae6b"` (common_dataset_release 의 dataset=adi 행. 이미 있음, 청크 0건)
  - 상수 `ECFR_RELEASE_ID = "0c2efcae-99ed-41ae-85b6-1af8c8fbc44c"` (현재 eCFR 색인. 테스트용 비교값)
  - 상수 `MAX_CHUNK_CHARS = 3000`
  - `letter_pages(parsed_dir: Path, letters_json: Path) -> dict[str, list[str]]`
  - `build_letter_chunks(source_key: str, pages: list[str], *, max_chars=MAX_CHUNK_CHARS) -> list[dict]`
  - `index_letter_chunk(chunk: dict, *, client, call_kanon2=call_kanon2_api) -> None`
  - `main()` — argparse: `--parsed`, `--letters`(기본 `[4]frontend/public/decision-letters.json`), `--limit`(시범용). 서한 → 청크 → 임베딩 → upsert. 이미 있는 chunk_key 는 건너뛴다
- 테스트(이미 작성됨, 수정 금지): `[2] db/tests/4_ADI+CAA/test_letter_chunk.py`

## Codex 메모

### 입력 파일 모양
- `decision-letters.json` (`[4]frontend/public/`, SUU-252 `dashboard_letters_json.build` 출력): `{"letters": [{source_key, facility_name, title, subparts, date, pdf_url}]}`. **`pdf_url` 이 null 이 아닌 것만** 쓴다 (132 중 128).
- `parsed/2026-09-22/adi_entry_document.jsonl`: `{source_system, source_key, version_id, ...}`. **`source_system == "caa_dashboard"`** 행만 본다. source_key → version_id.
- `parsed/2026-09-22/adi_page.jsonl`: `{version_id, page_no, text_content, status, ...}`. `status == "ok"` 인 페이지만, **page_no 오름차순** 으로 정렬해서 쓴다 (파일 순서를 믿지 않는다).
- 실제 폴더: `[2] db/4) ADI+CAA/parsed/2026-09-22/` (로컬 전용, 레포에 없음). 128건·465쪽·페이지 평균 3,000자.

### letter_pages
- 반환 `{source_key: [page1_text, page2_text, ...]}`. pdf_url 없는 서한, ADI 서한, 페이지가 하나도 없는 서한은 키 자체가 없다.

### build_letter_chunks — 자르는 규칙
1. 페이지를 `"\n"` 로 이어붙인다 (`"\n\n"` 아님 — 페이지 경계는 문단 경계가 아니다. 1쪽 끝 문장이 2쪽 첫 줄로 이어지는 걸 한 문장으로 두려는 것).
2. 이어붙인 본문을 `"\n\n"` 로 문단을 나눈다. 빈 문단은 버린다.
3. `ecfr_chunks._pack_in_order` 와 같은 방식: 문단을 순서대로 담다가 `max_chars` 를 넘으면 새 청크. 문단 하나가 `max_chars` 보다 크면(pypdf 본문은 빈 줄이 거의 없어 흔하다) 그 문단을 줄(`"
"`) 단위로 다시 담는다. 줄 하나가 `max_chars` 를 넘으면 그 줄 하나가 청크 하나. 글자를 버리지 않는다.
4. 반환 dict (rag_chunk 에 그대로 upsert 되는 컬럼 + source_key):
   ```python
   {
       "chunk_key": f"dashboard/{source_key}/{n}",   # n 은 0부터
       "source_key": source_key,
       "chunk_text": "...",
       "page_from": int, "page_to": int,           # 청크 첫 문단·끝 문단이 있던 페이지 번호
   }
   ```
   테스트가 `chunk_key` 순번 0,1,2… 와 `source_key`·`chunk_text` 만 본다. page_from/page_to 는 block_from/block_to 에 넣기 위한 것.

### index_letter_chunk — 저장
- `ecfr_chunk_index.index_chunk` 를 흉내내되 컨텍스트 LLM 호출이 없다. `call_kanon2` 는 `ecfr_chunk_index.call_kanon2_api` 를 기본값으로 재사용, 요청은 `ecfr_embed.build_embedding_request(context_text, chunk_text)` 로 만든다 (`task=retrieval/document`, `overflow_strategy=None`).
- `context_text` 는 LLM 없이 서한 메타데이터 한 줄로 만든다: `"EPA applicability determination letter: {title} — {facility_name} (40 CFR Part 63 Subpart {', '.join(subparts)})"`. 이걸 `chunk_text` 앞에 붙여 임베딩·BM25 둘 다에 쓴다 (백엔드 `load_index` 가 `context_text + chunk_text` 로 BM25 를 만든다). 메타데이터는 `letter_pages` 가 아니라 `main()` 에서 decision-letters.json 을 읽어 chunk dict 에 `context_text` 로 넣어주면 된다. 테스트 fixture 청크에는 `context_text` 가 없을 수 있으니 `chunk.get("context_text")` 로 다룬다(없으면 chunk_text 만 임베딩).
- upsert 행 (테이블 `rag_chunk`, `on_conflict="release_id,chunk_key"`). NOT NULL 컬럼: release_id, chunk_key, dataset, doc_key, node_key, block_from, block_to, chunk_text. FK 는 없다(확인함).
  ```python
  {
      "release_id": LETTER_RELEASE_ID, "chunk_key": chunk["chunk_key"],
      "dataset": "adi", "doc_key": source_key, "node_key": source_key,
      "block_from": page_from, "block_to": page_to,
      "source_locator": pdf_url,              # 있으면
      "chunk_text": ..., "context_text": ...,  # 없으면 None
      "content_hash": sha256(chunk_text + "\n\n" + (context_text or "")),
      "embed_model": "kanon-2-embedder", "embed_dims": 1792, "embedding": [...],
      "index_status": "embedded",
  }
  ```
  `rag_chunk` 에 `source_key` 컬럼은 없다. 서한별 묶음은 `doc_key`(= source_key) 로 한다. 테스트도 `doc_key` 를 본다.
- 실행 옵션: 동시 요청은 4개 이하(`WinError 10035` 이력, `[1] docs/3) rag/2_rag 구축 계획.md` [5]-4). 465쪽 ≈ 청크 500개 안팎이라 순차 실행도 몇 분이면 끝난다. 이미 `rag_chunk` 에 있는 `(LETTER_RELEASE_ID, chunk_key)` 는 건너뛴다.
- 환경변수: `SUPABASE_URL`, `SUPABASE_SECRET_KEY`(supabase-py `create_client`, `adi_ingest.py` 참고), `ISAACUS_API_KEY`.

### 격리 확인
- `match_rag_chunk(query, p_release_id, k)` 는 `where release_id = p_release_id` 라 eCFR release(`0c2efcae…`) 로 부르면 서한 청크가 안 나온다. 백엔드는 안 고친다. 적재 후 아래로 확인:
  ```sql
  select release_id, count(*) from rag_chunk where chunk_key like 'dashboard/%' group by 1;  -- 5cc370d0… 한 줄만
  ```
